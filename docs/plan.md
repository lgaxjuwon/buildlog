# BuildLog 단계별 개발 계획

## 1. 계획의 기준

현재 `docs/spec.md`의 기능과 조건을 기준으로 첫 버전을 개발하는 순서입니다. 화면은 React, 서버는 Python·FastAPI, 실제 서비스 DB는 Supabase의 PostgreSQL을 사용합니다. 우선 로컬 개발·테스트에는 SQLite3를 사용합니다. 화면과 서버는 API로 통신합니다.

이 문서는 개발 계획과 단계별 진행 상태를 관리합니다. 사용자 요청으로 Phase 1의 독립 가능한 기본 틀을 먼저 구현했습니다. 상세 결과는 `docs/phase1.md`에 기록합니다. Git 초기화·커밋·배포는 진행하지 않습니다. 소요 기간은 아직 정하지 않았으며, 미결정 사항이 있는 기능은 결정 후 진행합니다.

개발 순서는 **규칙 확인 → 기본 틀 → 회원과 권한 → 공부 기록 → 할 일 → 오류 기록 → 공개 기록과 검색 → 댓글·좋아요 → 신고 → 전체 확인**입니다. 기록을 먼저 만들고, 그 기록을 공유하거나 반응하는 기능을 뒤에 만듭니다.

## 2. 모든 단계에서 지킬 원칙

- 기능을 만들 때 정상 동작뿐 아니라 잘못된 입력, 처리 실패, 권한 제한도 함께 만듭니다.
- 화면에서 버튼을 숨기는 것만으로 끝내지 않고, 권한 없는 요청 자체가 처리되지 않게 합니다.
- 비공개는 세 종류 기록 모두의 기본값입니다. 비로그인 사용자는 공개 기록도 볼 수 없습니다.
- 실패했을 때 기존 저장 내용은 바꾸지 않으며, 입력 유지·비밀번호 지우기 등은 각 기능의 설명을 따릅니다.
- 글자 수, 공백 처리, 목록 정렬, 성공 후 이동 화면을 기능별로 구분합니다.
- 날짜는 자동으로 저장합니다. 수정 때문에 원래 작성순 정렬이 바뀌지 않게 원래 작성 시각과 수정 시각을 구분합니다.
- 기능별 완료 확인에는 화면 확인과 필요한 자동 검사를 함께 사용합니다. 특히 권한, 입력 경계, 상태 변경, 중복 저장 방지는 자동으로 확인할 수 있게 합니다.
- 미정·충돌 사항은 임의로 확정하지 않습니다. 해당 항목에 의존하는 작업 전에 하나씩 확인합니다.
- spec에 없는 기능은 편의상 추가하지 않습니다.
- 각 기능은 FastAPI의 데이터 처리·권한 검사와 React의 화면 동작을 연결한 뒤 완료로 판단합니다.
- SQLite3와 Supabase에서 같은 사용자 규칙을 적용합니다. DB 연결 설정과 저장 처리를 분리하여 전환을 준비하고, 첫 버전 완료 전에 Supabase에서도 검증합니다.

## 4. Phase 0 — 규칙과 완료 기준 정리

### 진행할 일

1. spec의 각 기능을 작업 목록과 확인 목록으로 옮깁니다.
2. 사용자 역할을 가입 전 사용자, 로그인한 작성자, 다른 로그인 사용자, 운영자로 구분합니다.
3. 각 역할이 볼 수 있는 것과 바꿀 수 있는 것을 정리합니다. 운영자에게는 명시된 신고 열람 기능만 계획합니다.
4. 아래 충돌·누락 사항을 관련 기능 개발 전에 하나씩 확인합니다.
5. 답을 받은 규칙은 spec에 반영한 뒤 해당 작업의 기준으로 사용합니다.

### 완료 기준

- 각 기능의 개발 단계와 확인 항목이 연결되어 있습니다.
- 공통 구조를 결정하는 데 필요한 질문이 해결되어 있습니다.
- 나중에 확인할 항목은 담당 단계가 표시되어 있습니다.

## 5. Phase 1 — 실행 환경과 공통 화면 준비

### 진행 순서

1. 기존 폴더와 파일을 확인하고 현재 내용을 보존합니다. 기존 README는 별도 요청 없이 변경하지 않습니다.
2. Python·FastAPI 및 Node.js·React의 호환되는 안정 버전과 필요한 도구를 정하고 기록합니다. 구체적인 버전은 개발 시작 시 확인합니다.
3. `frontend`에는 React 화면, `backend`에는 FastAPI 서버, `database`에는 DB 구조·변경 관리 자료와 로컬 테스트 DB를 둘 구성을 정합니다. `docs`에는 개발 문서를 유지합니다.
4. Python 가상 환경과 React 개발 환경, FastAPI 실행 환경, SQLite3 저장 위치를 준비합니다. 결정한 DB 접근 도구로 환경별 DB 연결을 분리하고 Supabase에도 적용할 구조 변경 방법을 마련합니다.
5. 비밀 설정은 추적하지 않고 `.env.example`에는 비밀값 없는 항목 예시만 둡니다. 기존 `.gitignore` 규칙을 유지합니다.
6. 밝은 배경, 카드, 메뉴, 입력칸, 버튼, 오류 안내의 공통 모양을 만듭니다.
7. 회원가입·로그인·내 기록 홈·계정 설정·각 기록·공개 기록 화면의 이동 경로를 잡습니다. 실제 데이터 기능은 이후 단계에서 연결합니다.
8. 너비 360px부터 컴퓨터 크기까지 사용할 수 있는 화면 틀을 마련합니다.
9. React에서 FastAPI로 요청을 보내 결과를 표시하는 연결을 확인합니다. 개발용 화면·서버 주소와 허용할 요청 출처를 설정합니다.
10. 화면용 API 주소, 서버용 DB 연결 등 환경별 설정 항목을 문서화합니다. 로컬 SQLite3 시작에 Supabase 비밀값을 필수로 요구하지 않습니다. 선택한 인증 방식이 외부 연결을 필요로 한다면 필요한 설정을 먼저 안내하고 별도 확인합니다.

### 완료 기준

- React 화면과 FastAPI 서버가 실행되고 서로 통신하며 SQLite3를 사용할 수 있습니다.
- DB 구조를 SQLite3와 Supabase에 적용하는 방법 및 환경별 연결 설정이 정리되어 있습니다.
- 기본 화면이 360px에서 겹치거나 화면 밖으로 나가지 않습니다.
- 비밀값이 예시 파일이나 추적 대상 파일에 들어가지 않습니다.
- 재실행에 필요한 최소한의 안내는 별도 개발 문서에 남깁니다.

## 6. Phase 2 — 회원과 접근 권한

### 진행 순서

1. Phase 0에서 결정한 인증 방식으로 회원 구조를 만듭니다. 직접 인증이면 서버에서 비밀번호를 안전하게 보관하고, Supabase Auth 사용이면 비밀번호 처리를 해당 인증 서비스에 맡깁니다. 어느 방식이든 이메일·닉네임 중복과 기존 회원 규칙을 지킵니다.
2. 가입 화면에 이메일·비밀번호·닉네임 입력과 검사를 연결합니다.
3. 이메일·닉네임의 앞뒤 공백을 제거합니다. 비밀번호는 입력 그대로 처리합니다.
4. 비밀번호 8~64자, 닉네임 2~20자 및 한글·영문·숫자·밑줄 조건을 적용합니다.
5. 가입 성공 시 로그인 화면으로 이동합니다. 실패 시 이메일·닉네임은 유지하고 비밀번호는 지웁니다.
6. 이메일·비밀번호 로그인과 성공 후 내 기록 홈 이동을 연결합니다. 실패 시 이메일은 유지하고 비밀번호는 지웁니다.
7. 비로그인 사용자가 모든 기록 화면에 접근하지 못하게 합니다.
8. 계정 설정에서 자신의 닉네임만 변경하게 하고 중복·길이·문자 조건을 동일하게 적용합니다.
9. 이후 공개 기록·댓글이 현재 계정의 닉네임을 보여주도록 연결 기준을 마련합니다.

### 완료 확인

- 서로 다른 두 계정으로 가입·로그인·닉네임 변경이 됩니다.
- 중복 이메일·닉네임, 잘못된 이메일, 비밀번호 7·65자, 닉네임 범위 밖 입력이 거절됩니다.
- 비밀번호 8·64자, 닉네임 2·20자의 경계값을 확인합니다.
- 실패 시 입력 유지·비밀번호 제거가 설명서대로 동작합니다.
- 다른 계정의 닉네임을 바꿀 수 없습니다.
- 공개 기록을 포함한 기록 화면의 비로그인 접근이 차단됩니다.

## 7. Phase 3 — 공부 기록과 공통 기록 처리

### 진행 순서

1. 작성자, 제목, 내용, 공개 여부, 작성 시각, 수정 시각을 저장하도록 구성합니다.
2. 제목 1~100자·내용 1~5,000자 검사와 앞뒤 공백 제거를 적용합니다. 중간 띄어쓰기는 유지하고 공백만 있는 값은 거절합니다.
3. 작성 화면에서 저장하면 기본 비공개로 보관하고 공부 기록 목록으로 이동합니다.
4. 내 목록을 최근 작성순으로 보여주고 선택한 기록의 상세 내용을 연결합니다.
5. 작성자만 수정하게 하고 수정 시각을 저장·상세 표시한 뒤 목록으로 이동합니다.
6. 작성자만 삭제하게 하고 확인창에 동의한 경우에만 삭제합니다.
7. 내 기록의 제목·내용에 검색어가 포함되는 검색을 연결합니다. 검색어 앞뒤 공백을 제거하고 빈 검색어는 전체 목록으로 처리합니다.
8. 작성·수정 실패 시 입력값 유지, 수정·삭제 실패 시 기존 내용 보존, 조회 실패 안내를 연결합니다.
9. 작성자만 비공개를 읽고 다른 로그인 사용자는 공개만 읽게 하는 검사를 기록 조회·수정·삭제에 적용합니다.

### 완료 확인

- 작성 → 목록 → 상세 → 수정 → 삭제 흐름을 사용할 수 있습니다.
- 최소·최대 길이 및 초과·빈 입력·공백 처리가 정확합니다.
- 작성·수정 날짜, 성공 후 목록 이동, 실패 시 입력 유지가 정확합니다.
- 제목과 내용 각각의 단어로 내 기록을 검색할 수 있습니다.
- 두 계정과 비로그인 상태에서 열람·수정·삭제 권한을 확인합니다. 주소를 직접 열어도 제한이 적용됩니다.

## 8. Phase 4 — 할 일과 완료 상태

### 진행 순서

1. 작성자·제목·공개 여부·완료 여부·작성 및 수정 시각·완료 시각을 저장합니다. 작성 시각은 정렬 기준으로 사용합니다.
2. 제목 1~100자, 앞뒤 공백 제거, 공백만 입력 거절을 적용합니다.
3. 새 할 일은 미완료·기본 비공개로 저장하고 목록으로 이동합니다.
4. 전체·남은 일·완료한 일 목록을 만들고 미완료 우선, 같은 상태는 최근 작성순으로 정렬합니다.
5. 완료 체크 시 완료 시각을 저장하고 취소 시 완료 시각을 지웁니다.
6. 제목·공개 여부 수정과 확인창을 거치는 삭제를 연결합니다.
7. 수정 시각을 목록 항목에 표시하고 수정 성공 후 목록으로 이동합니다.
8. 실패 시 기존 상태 보존과 작성·수정 입력 유지, 작성자 권한 검사를 연결합니다.

### 완료 확인

- 작성·수정·삭제, 완료와 취소, 세 가지 필터가 동작합니다.
- 완료 항목은 전체·완료한 일 목록에 남습니다.
- 완료 시각 생성·취소 시 제거, 정렬, 수정 시각 표시가 맞습니다.
- 다른 사용자는 공개 할 일을 읽을 수 있지만 변경할 수 없습니다.
- 내 할 일 검색, 마감일, 중요도 기능을 추가하지 않았습니다.

## 9. Phase 5 — 오류 기록과 해결 처리

### 진행 순서

1. Phase 0의 ‘새 오류 초기 상태’ 충돌을 먼저 해결하고 spec에 반영합니다.
2. 작성자·오류 제목·오류 내용·해결 방법·해결 여부·공개 여부·작성 및 수정 시각·해결 시각을 저장합니다.
3. 제목 1~100자, 오류 내용 1~5,000자, 입력한 해결 방법 1~5,000자 조건을 적용합니다. 앞뒤 공백은 제거하고 중간 띄어쓰기는 유지합니다.
4. 해결 방법이 비어 있는 미해결 기록을 저장할 수 있게 합니다. 해결 상태에는 해결 방법을 필수로 받습니다.
5. 목록·상세와 전체·미해결·해결 필터를 연결하고 최근 작성순으로 보여줍니다.
6. 내 오류 제목·오류 내용으로 검색합니다. 내 검색에는 해결 방법을 임의로 추가하지 않습니다.
7. 해결 시 해결 시각을 저장하고 미해결로 되돌리면 해결 방법은 유지하되 해결 시각은 지웁니다.
8. 수정 시각을 상세에 표시하고 작성·수정 성공 후 오류 목록으로 이동합니다. 삭제는 확인창 동의 후 진행합니다.
9. 실패 시 입력 유지·기존 기록 보존과 작성자 권한 검사를 적용합니다.

### 완료 확인

- 미해결 저장 → 상세 읽기 → 해결 방법 입력 → 해결 → 미해결 전환을 확인합니다.
- 해결 방법 없는 해결 처리는 거절됩니다.
- 제목·내용·해결 방법 길이와 공백 처리가 정확합니다.
- 상태별 목록, 내 검색 범위, 정렬, 날짜 저장·제거·표시가 맞습니다.
- 수정·삭제 확인과 다른 사용자 변경 차단이 동작합니다.

## 10. Phase 6 — 공개 기록 목록과 통합 검색

### 진행 순서

1. 공부 기록·할 일·오류 기록의 공개 항목을 한 화면에서 모아봅니다.
2. 종류별 필터와 최근 작성순 정렬을 적용합니다.
3. 공개 공부 기록은 제목·내용, 공개 할 일은 제목, 공개 오류 기록은 제목·오류 내용·해결 방법을 검색합니다.
4. 검색어 앞뒤 공백을 제거하고 빈 검색어는 전체 공개 목록으로 처리합니다. 필터와의 결합은 앞서 확인한 규칙을 적용합니다.
5. 각 항목에서 공개 내용을 읽도록 연결하고 현재 작성자의 닉네임을 표시합니다.
6. 공개→비공개 변경 시 공개 목록·검색·상세에서 다른 사용자의 접근을 막습니다.
7. 조회 실패는 저장된 데이터를 바꾸지 않고 안내합니다.

### 완료 확인

- 세 종류 공개 기록이 종류별 필터와 검색 범위에 맞게 나타납니다.
- 공개 오류의 해결 방법으로는 검색되며 내 오류 검색과 범위가 구분됩니다.
- 닉네임 변경이 과거 공개 기록에도 반영됩니다.
- 비공개 기록이 목록·검색에 섞이거나 주소로 노출되지 않습니다.
- 비로그인 사용자는 공개 목록·검색·상세를 열 수 없습니다.

## 11. Phase 7 — 댓글과 좋아요

### 진행 순서

1. 공개 공부·오류 기록에만 댓글과 좋아요를 연결합니다. 공개 할 일에는 제공하지 않습니다.
2. 댓글 내용 1~500자, 앞뒤 공백 제거, 공백만 입력 거절을 적용합니다.
3. 댓글을 오래된 순서로 보여주고 현재 작성자의 닉네임을 표시합니다.
4. 댓글 작성자는 자신의 댓글을 수정·삭제하게 합니다. 기록 작성자는 해당 기록의 댓글을 삭제할 수 있지만 남의 댓글을 수정할 수는 없게 합니다.
5. 확인된 삭제 확인창 규칙을 적용하고 댓글 처리 실패 시 입력 유지·기존 내용 보존을 연결합니다.
6. 사용자별 기록당 좋아요 하나만 저장하며 다시 누르면 취소합니다. 현재 사용자의 누름 상태와 전체 개수를 표시합니다.
7. 기록을 비공개로 바꾸면 댓글·좋아요를 삭제하지 않고 다른 사용자에게 숨깁니다. 다시 공개하면 복원해 보여줍니다.
8. 좋아요 실패 시 기존 상태를 유지합니다. 비공개·삭제된 대상에 대한 처리도 접근 권한을 다시 확인합니다.

### 완료 확인

- 1·500자 댓글은 등록·수정되고 빈 값·501자는 거절됩니다.
- 댓글 작성자·기록 작성자·제3자의 권한 차이가 정확합니다.
- 닉네임 변경이 과거 댓글에도 반영됩니다.
- 좋아요 누름·취소·개수 표시와 중복 방지가 동작합니다.
- 공개→비공개→공개 전환 후 댓글·좋아요가 보존됩니다.
- 할 일 댓글·좋아요와 댓글 답글을 추가하지 않았습니다.

## 12. Phase 8 — 신고와 운영자 열람

### 진행 순서

1. 세 종류 공개 기록과 댓글에 신고 입력을 연결합니다.
2. 신고 이유 1~500자와 앞뒤 공백 제거를 적용하고 공백만 입력하면 거절합니다.
3. 신고자·대상·신고 이유를 보관하고 같은 사용자의 같은 대상 중복 신고를 막습니다.
4. 접수 성공 안내, 이미 신고한 대상 안내, 실패 시 이유 입력 유지를 적용합니다.
5. 운영자만 신고 목록과 내용을 볼 수 있게 합니다. 위치와 접근 방법은 사전 결정한 방식을 사용합니다.
6. 신고만으로 대상이 자동 삭제되지 않게 합니다. 신고 대상이 비공개가 되어도 운영자는 신고를 계속 확인할 수 있게 합니다.
7. 대상 삭제 후 보관 정보는 Phase 0에서 합의한 규칙을 적용합니다.

### 완료 확인

- 공개 기록 세 종류와 댓글 모두 신고할 수 있습니다.
- 이유 1·500자는 접수되고 빈 값·501자는 거절됩니다.
- 동일 사용자·동일 대상 중복은 막고 다른 사용자 신고와 구분합니다.
- 신고 성공·실패 안내와 입력 유지가 맞습니다.
- 일반 사용자·비로그인 사용자는 신고 목록을 열 수 없습니다.
- 운영자는 비공개 전환 후에도 신고를 확인할 수 있습니다.
- 자동 삭제나 신고 처리 상태 기능을 추가하지 않았습니다.

## 13. Phase 9 — Supabase 연결·전체 흐름·반응형 확인

### 진행 순서

0. Supabase 프로젝트와 테스트할 DB 연결을 준비합니다. 선택한 인증 방식에 필요한 설정도 확인합니다. 서버용 비밀 설정을 로컬 환경에 입력하고, DB 구조를 적용한 뒤 별도 테스트 데이터로 핵심 흐름을 검증합니다. 기존 SQLite3 데이터 이전은 결정한 경우에만 진행합니다. DB별 검색·정렬·날짜·중복 제한·권한 차이를 확인하고 SQLite3 결과만으로 완료 처리하지 않습니다.
1. 각 단계에서 통과한 자동 검사와 화면 확인 결과를 모읍니다. 변경된 부분과 연결된 흐름을 다시 확인합니다.
2. 가입 → 로그인 → 내 기록 홈 → 세 종류 기록 작성 → 공개 → 다른 계정 열람 → 댓글·좋아요 → 신고 → 운영자 확인 흐름을 실행합니다.
3. 공개 취소, 닉네임 변경, 완료·해결 취소, 삭제 동의 취소 등 상태를 되돌리는 흐름도 확인합니다.
4. 새로고침·다시 접속한 뒤 기록과 상태가 남는지 확인합니다.
5. 작성자·다른 로그인 사용자·비로그인 사용자·운영자로 권한을 점검합니다. 버튼 외에 직접 주소와 요청으로도 확인합니다.
6. 입력 오류와 저장·조회 실패를 재현하여 안내, 입력 유지, 기존 내용 보존을 확인합니다.
7. 너비 360px 이상에서 글자·카드·입력칸·버튼의 겹침과 잘림을 확인합니다.
8. 확인 당시의 Chrome·Edge·Safari 최신 두 버전을 기록하고 주요 흐름을 확인합니다. 접근 가능한 기기가 없으면 미확인으로 표시하고 검증할 환경을 확보합니다.
9. 발견한 문제를 고친 뒤 영향을 받은 기능을 재확인합니다.
10. spec 항목별 완료·미완료·확인 필요 결과를 문서로 남깁니다. 공개 배포는 별도 작업이며 이 계획의 완료 조건에 넣지 않습니다.

### 최종 완료 기준

- spec의 회원·닉네임·공개 범위·세 종류 기록·검색·댓글·좋아요·신고·반응형 조건이 모두 확인되었습니다.
- React·FastAPI 연결과 SQLite3 테스트가 완료되고 Supabase에서도 핵심 기능·권한·중복 방지·검색·정렬·날짜 처리가 확인되었습니다.
- 입력 경계, 공백 처리, 정렬, 자동 날짜, 성공 후 이동, 실패 처리와 권한이 기능별 조건에 맞습니다.
- 운영자 신고 열람을 포함해 한 기능에서 만든 데이터가 다음 기능에 올바르게 연결됩니다.
- 구현에 영향을 주는 확인 필요 사항이 해결되어 문서와 실제 동작이 일치합니다.
- 지원 브라우저와 화면 크기 검증 결과가 남아 있으며 미확인 항목을 완료로 표시하지 않았습니다.
- 이메일 확인·비밀번호 찾기·할 일 마감일·중요도·내 할 일 검색·댓글 답글은 포함하지 않았습니다.

## 14. 진행 상황 표시 방법

각 Phase는 아래 순서로 관리합니다.

1. **준비:** 필요한 결정과 앞 단계의 완료 여부를 확인합니다.
2. **개발:** 해당 Phase의 기능과 실패·권한 처리를 구현합니다.
3. **확인:** 위 완료 확인 항목을 실행합니다.
4. **완료:** 결과와 남은 문제를 기록합니다. 필수 조건이 미완료이면 Phase를 완료로 표시하지 않습니다.

현재 상태는 **Phase 0 결정 확인 중, Phase 1 기본 틀 구현·검증 완료 및 일부 보류**입니다. [phase0.md](phase0.md)에 미결정 사항과 권한표, [phase1.md](phase1.md)에 구현·검증 결과를 정리했습니다. 회원 인증 방식과 실제 홈 카드 구성은 아직 미정이므로 Phase 0·1 전체를 완료로 표시하지 않습니다. 사용자 기능은 후속 Phase에서 구현합니다.

## 15. 사용자 준비 사항

- **지금(Phase 0):** 설치나 비밀값 전달은 필요 없습니다. 인증 방식 등 구조에 영향을 주는 결정을 하나씩 확인합니다. 이전의 신고 대상 삭제 후 보관 질문도 아직 미결정 상태입니다.
- **Phase 1:** Python과 Node.js 설치 상태를 확인하고 필요한 경우 설치를 안내합니다. 개발용 주소와 포트 등은 환경 확인 후 정리합니다.
- **Supabase 연결 시점:** 사용자가 접근 가능한 Supabase 프로젝트와 DB 연결 설정이 필요합니다. Supabase Auth를 선택하면 Phase 2 이전부터 관련 프로젝트 설정이 필요할 수 있습니다.
- **비밀값 입력:** 실제 비밀번호·연결 비밀값은 채팅이나 문서에 적지 않고 안내받은 서버 로컬 환경 설정에 직접 입력합니다.
- **최종 화면 확인:** Safari 검증에는 해당 브라우저를 사용할 수 있는 환경이 필요합니다. 준비되지 않은 환경은 미확인으로 남깁니다.
